## Tool contract

### Name and input schema

```text
get_catalog_item
```

Generated by Spring AI 2.0.1 from the annotated adapter method and verified in unit
tests and by inspecting `tools/list` on the running server:

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "additionalProperties": false,
  "properties": {
    "id": {
      "type": "integer",
      "description": "Catalog item identifier. Must be a positive integer, for example 16. Use search_catalog to discover identifiers."
    }
  },
  "required": ["id"]
}
```

`id` is the only input, it is required, unknown arguments are rejected, and the
parameter carries an explicit description. Consistent with the accepted Slice 5 policy,
the schema declares **no** `minimum`/`maximum`/`exclusiveMinimum`: the MCP SDK validates
arguments against the schema before the handler runs, so encoding the positive-identifier
rule would reject out-of-range values with a generic schema error and relocate the rule
out of `CatalogService`. The bound is stated in the description instead; `CatalogService`
enforces it. A unit test asserts the absence of those keywords.

### Output shape

`tools/call` returns `isError: false` with a single `content[0]` block
`{"type":"text","text":"<JSON item>"}`. The JSON is the item object itself — the same
shape as one element of `search_catalog`'s `items` array, because both tools map through
the shared `SearchCatalogItem` record. Raw text captured from the live server:

```json
{"id":16,"sku":"SVC-104","name":"Network Health Assessment","type":"SERVICE",
"description":"Review office network configuration and provide a prioritized findings report.",
"price":199.00,"active":true,"createdAt":"2026-01-15T09:00:00Z","updatedAt":"2026-01-15T09:00:00Z"}
```

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | integer | catalog item ID |
| `sku` | string | stock-keeping unit |
| `name` | string | display name |
| `type` | string | `PRODUCT` or `SERVICE` |
| `description` | string | business description |
| `price` | number | price, two decimal places preserved (`199.00`) |
| `active` | boolean | active/inactive flag |
| `createdAt` | string | ISO-8601 UTC instant |
| `updatedAt` | string | ISO-8601 UTC instant |

Timestamp formatting consistency with `search_catalog` is not just asserted by pattern:
the integration suite invokes `get_catalog_item(id=16)` and `search_catalog(text=SVC-104)`
and asserts the two parsed payloads are deeply equal, including
`createdAt`/`updatedAt` = `2026-01-15T09:00:00Z`.

Delivery is text content rather than MCP `structuredContent`, for the same
framework-determined reason documented in Slice 5: Spring AI 2.0.1's
`McpToolUtils.toSyncToolSpecification` never sets `outputSchema`.

## Registration mechanism

Unchanged. `McpToolConfiguration` still exposes exactly one `ToolCallbackProvider` bean,
now built from both annotated adapter objects:

```java
ToolCallback[] callbacks = Stream.of(searchCatalogTool, getCatalogItemTool)
    .flatMap(adapter -> Stream.of(ToolCallbacks.from(adapter)))
    .map(OptionalArgumentsToolCallback::new)
    .toArray(ToolCallback[]::new);
return ToolCallbackProvider.from(callbacks);
```

`ToolCallbackConverterAutoConfiguration` converts those callbacks into
`McpServerFeatures.SyncToolSpecification` entries. No custom registrar, no manual
`SyncToolSpecification` wiring, and no replacement of the accepted mechanism. Because
`search_catalog`'s `ToolDefinition` is untouched, its name, description and schema are
byte-identical to the Slice 5 contract — confirmed by the unchanged
`SearchCatalogToolTest`/`OptionalArgumentsToolCallbackTest` hashes and the unchanged live
schema.

## Mapping to CatalogService

```text
MCP tools/call arguments {id}
  -> GetCatalogItemTool.getCatalogItem(Long id)
  -> CatalogService.getItem(id)          [positive-ID validation, lookup, not-found]
  -> CatalogItemView
  -> SearchCatalogItem                   [shared shape + ISO-8601 UTC formatting]
```

- The identifier is passed through unchanged (`null`/`0`/negative included); the adapter
  performs no validation and no lookup of its own.
- `GetCatalogItemTool`'s only field and constructor parameter is `CatalogService`; a unit
  test asserts the adapter type never references `catalog.persistence`, and a behavioral
  test verifies the only call made is `CatalogService.getItem`.
- Detail lookup applies no active/type filter — inactive rows are retrievable by
  identifier, matching `CatalogService.getItem`; this is asserted live for id 22
  (`SVC-110`, inactive).
- No MCP type enters `catalog.application`: the adapter reuses `CatalogItemView` and the
  shared `SearchCatalogItem`, and adds no request/response type to the service layer.

## Not-found and error behavior

| Case | Path | MCP result |
| --- | --- | --- |
| Unknown identifier (e.g. `99999`) | `CatalogService.getItem` → `CatalogItemNotFoundException` | `isError: true`, text `Catalog item not found: 99999` |
| Non-positive identifier (`0`, `-5`) | `CatalogService.getItem` → `InvalidCatalogCriteriaException` | `isError: true`, text `Catalog item ID must be positive` |
| `id` omitted | SDK `ToolInputValidator` before the handler | `isError: true`, text `Tool (get_catalog_item) input validation failed: Validation failed: JSON schema validation errors: [: required property 'id' not found]` |
| Non-integer `id` (e.g. `"not-a-number"`) | SDK `ToolInputValidator` before the handler | `isError: true`, text `Tool (get_catalog_item) input validation failed: Validation failed: JSON schema validation errors: [/id: string found, integer expected]` |

`MethodToolCallback` preserves the cause message when wrapping invocation exceptions
(`ToolExecutionException` uses `cause.getMessage()`), and `McpToolUtils` converts any
thrown exception into a single text block with `isError: true`. No stack trace, no
secret, no SQL text and no fabricated item is returned; tests assert this explicitly for
every case above, and a dedicated test asserts the not-found text is not a JSON item
payload.

## Deviations, compatibility notes, risks

**PRD/plan deviations.** None of substance. The tool implements FR-2, FR-3 and FR-3A for
detail lookup, completes the Phase 1 MCP tool inventory (`search_catalog` +
`get_catalog_item`), and keeps the accepted registration mechanism and both Slice 3/4
behaviors. The only implementation notes are:

1. Three pre-existing **registry-inventory** assertions advanced to include the second
   production tool; no behavioral assertion and no `search_catalog` production source
   changed.
2. `get_catalog_item` reuses the existing `SearchCatalogItem` record rather than
   introducing a near-duplicate detail record. This is deliberate: it guarantees the
   field set, price scale and timestamp formatting are identical across both tools, which
   is a required property of this slice.

**Compatibility findings.** No new framework constraint. The generated schema,
`required` enforcement, error path and result serialization all behave as documented; the
Slice 5 `outputSchema`/`structuredContent` limitation still applies and is unchanged.

**Unresolved risks/questions.**

1. **Framework-level schema-validation errors** for missing/wrong-typed `id` are
   pre-handler and use the SDK's own wording (`Tool (get_catalog_item) input validation
   failed: ...`). They are defined, safe and non-fabricating, but the wording is owned by
   the MCP SDK and could change on upgrade. Service-level errors are stable.
2. **Error text is the raw exception message.** Unchanged from Slice 5: a safe message for
   `CatalogItemNotFoundException`/`InvalidCatalogCriteriaException`, but an unexpected
   failure could surface an internal message. Phase 1 has no MCP error-sanitization layer.
3. **No `outputSchema`/`structuredContent`**, inherited from the accepted Slice 5
   mechanism.
4. **Inherited Slice 4 risks remain** (browser-origin allowlist for a future Inspector UI,
   container-hostname `Host` rejection, transport-bean override tracking the framework).

No rollback was needed: `get_catalog_item` calls `CatalogService`, preserves the accepted
not-found behavior, changes neither the `search_catalog` contract nor MCP security, and
does not broaden Phase 1 scope. **Slice 7 remains unstarted.**
