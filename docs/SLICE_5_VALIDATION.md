## Tool contract

### Name and input schema

```text
search_catalog
```

Generated by Spring AI 2.0.1 from the annotated adapter method (not hand-written) and
verified both in unit tests and by inspecting `tools/list` on the running server:

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "additionalProperties": false,
  "properties": {
    "type":     { "type": "string",  "description": "Optional item type filter. Must be exactly PRODUCT or SERVICE. Omit to include both types." },
    "active":   { "type": "boolean", "description": "Optional active-status filter. true returns only active items, false returns only inactive items. Omit to include both." },
    "maxPrice": { "type": "number",  "description": "Optional inclusive maximum price, for example 200 or 199.99. Must be at least 0, at most 9999999999.99, and have no more than two decimal places. Omit for no price limit." },
    "text":     { "type": "string",  "description": "Optional literal text matched case-insensitively anywhere in the SKU, name or description. At most 200 characters. Omit for no text filter." },
    "page":     { "type": "integer", "description": "Optional zero-based page number. Defaults to 0. Must be between 0 and 10000." },
    "pageSize": { "type": "integer", "description": "Optional number of items per page. Defaults to 20. Must be between 1 and 100." }
  },
  "required": []
}
```

`additionalProperties: false` rejects unknown arguments. Every parameter is optional
(`required` is empty) and every parameter carries an explicit description.

**Deliberate omission of bounds and enums.** The MCP SDK validates incoming arguments
against this schema *before* invoking the handler
(`io.modelcontextprotocol.util.ToolInputValidator`, `validateToolInputs=true` by
default). Encoding `enum`, `minimum`, `maximum` or `maxLength` in the schema would
therefore reject `pageSize=1000`, `type=FOO` or `maxPrice=-1` with a generic
schema-validation error and would move those rules out of `CatalogService`. Instead
the bounds are stated in the parameter *descriptions* so the model can avoid them,
while `CatalogService` remains the single enforcing authority. This is verified by a
unit test asserting that no property declares `enum`, `minimum`, `maximum`,
`exclusiveMinimum`, `exclusiveMaximum`, `minLength` or `maxLength`, and by integration
tests asserting the exact `CatalogService` message for each invalid input.

### Structured output shape

`tools/call` returns a normal MCP result (`isError: false`) whose single `content[0]`
block is `{"type":"text","text":"<JSON document>"}`. Raw text captured from the live
server:

```json
{"items":[{"id":13,"sku":"SVC-101","name":"Workstation Setup","type":"SERVICE",
"description":"Configure one employee workstation, install approved software and verify access.",
"price":149.00,"active":true,"createdAt":"2026-01-15T09:00:00Z","updatedAt":"2026-01-15T09:00:00Z"}],
"page":0,"pageSize":2,"totalItems":6,"totalPages":3}
```

| Field | Type | Meaning |
| --- | --- | --- |
| `items[]` | array | catalog items in the requested page, `id ASC` |
| `items[].id` | integer | catalog item ID |
| `items[].sku` | string | stock-keeping unit |
| `items[].name` | string | display name |
| `items[].type` | string | `PRODUCT` or `SERVICE` |
| `items[].description` | string | business description |
| `items[].price` | number | price, two decimal places preserved (`149.00`) |
| `items[].active` | boolean | active/inactive flag |
| `items[].createdAt` | string | ISO-8601 UTC instant |
| `items[].updatedAt` | string | ISO-8601 UTC instant |
| `page` | integer | zero-based page actually served |
| `pageSize` | integer | effective page size |
| `totalItems` | integer | total matching rows, independent of the page |
| `totalPages` | integer | ceiling division; `0` when nothing matches |

Errors use `isError: true` with the same single text block carrying the
`CatalogService` message, for example `Page size must be between 1 and 100` or
`Type must be PRODUCT or SERVICE`. No stack trace, secret or fabricated success is
returned.

**Framework-determined delivery.** Spring AI 2.0.1's `McpToolUtils.toSyncToolSpecification`
builds the MCP `Tool` from the callback's `ToolDefinition` (name, description,
inputSchema) and **never sets `outputSchema`**; results are returned as text content
only, with no `structuredContent`. Adding `outputSchema`/`structuredContent` would
require bypassing the accepted `ToolCallback` registration for a raw
`SyncToolSpecification` bean, which the task forbids. The JSON document above is
therefore the contract, and it is fully machine-readable.

## Registration mechanism

Unchanged from Slice 4: Spring AI `ToolCallback` / `ToolCallbackProvider` beans are
converted by `ToolCallbackConverterAutoConfiguration` into
`McpServerFeatures.SyncToolSpecification` and registered on the `McpSyncServer`.
`McpToolConfiguration` exposes one `ToolCallbackProvider` built from
`ToolCallbacks.from(searchCatalogTool)`, so name, description, schema and argument
binding stay framework-generated. No custom registrar and no manual
`SyncToolSpecification` wiring was added.

The only wrapper is `OptionalArgumentsToolCallback`: MCP `tools/call` makes
`arguments` optional, but `McpToolUtils` forwards it verbatim and Spring AI's
`MethodToolCallback` then fails with `toolArguments must not be null` when no
arguments were sent. The decorator maps an absent/blank/JSON-`null` payload to `{}`
and forwards every other payload unchanged; it does not touch the tool definition,
schema or binding. Without it the natural no-filter call would be unusable.

## Mapping to CatalogService

```text
MCP tools/call arguments
  -> SearchCatalogTool.searchCatalog(type, active, maxPrice, text, page, pageSize)
  -> new CatalogSearchCriteria(type, active, maxPrice, text, page, pageSize)
  -> CatalogService.search(criteria)          [defaults, validation, filtering, ordering, LIMIT/OFFSET]
  -> CatalogPage
  -> SearchCatalogResult / SearchCatalogItem  [shape + timestamp formatting only]
```

- Every argument is passed through exactly as received. An omitted argument stays
  `null`, so `page=0`/`pageSize=20` defaults and all bounds remain in `CatalogService`.
- The adapter contains no filtering, ordering, pagination arithmetic, SQL or
  repository access. `SearchCatalogTool`'s only field and constructor parameter is
  `CatalogService`.
- `InvalidCatalogCriteriaException` is not caught or reformatted; it propagates so the
  MCP error text is the service's own message.
- MCP-facing `SearchCatalogResult`/`SearchCatalogItem` live in the adapter package, so
  no MCP type enters `catalog.application`; the adapter reuses `CatalogService`,
  `CatalogSearchCriteria` and `CatalogPage` rather than duplicating them.

## Deviations, compatibility notes, risks

**PRD/plan deviations.** None of substance. The tool implements FR-1, FR-3 and FR-3A
for search. Two implementation notes:

1. Two Slice 4 guard-test expectations were advanced as described above. This is the
   only sense in which a pre-existing test changed.
2. `OptionalArgumentsToolCallback` is a small adapter-level normalization added because
   Spring AI's own path rejects an omitted `arguments` field. It does not change the
   registration mechanism, the schema or the service call.

**Compatibility findings.** The generated input schema, the error path and the result
serialization all work as intended on Spring AI 2.0.1 / MCP SDK 2.0.0. The one material
framework constraint is that `outputSchema`/`structuredContent` are not reachable
through the accepted `ToolCallback` conversion; the structured JSON text document is
used instead. This is recorded in `docs/ARCHITECTURE.md`.

**Unresolved risks/questions.**

1. **Error text is the raw exception message.** `McpToolUtils` converts any thrown
   exception into `isError:true` with `exception.getMessage()`. For
   `InvalidCatalogCriteriaException` this is a safe, intended message, but an unexpected
   failure (for example a database outage) could surface an internal message. Phase 1 has
   no MCP error-sanitization layer; this is deferred hardening, consistent with the PRD's
   "not production-hardened" Phase 1 statement.
2. **No `outputSchema`/`structuredContent`.** Hosts that prefer MCP structured content
   over JSON text must parse `content[0].text`. Revisit only with an approved change to
   the registration mechanism.
3. **Argument-count limits.** `text` longer than 200 characters, `page > 10000` and
   `pageSize > 100` are rejected rather than clamped, matching Slice 3's accepted policy.
   Callers relying on clamping would see errors instead.
4. **Inherited Slice 4 risks remain** (browser-origin allowlist for a future Inspector
   UI, container-hostname `Host` rejection, transport-bean override tracking the
   framework).

No rollback was needed: `search_catalog` uses `CatalogService`, changes no accepted
validation rule, and keeps the accepted registration mechanism. **Slice 6 remains
unstarted.**
